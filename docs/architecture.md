# EduRAG 架构理解笔记

日期：2026-07-08

当前目标：先理解原项目，不急着魔改。

## 1. 一句话架构

EduRAG 是一个“FAQ 精确问答 + RAG 知识库问答 + 大模型生成 + API/WebUI”的教育问答系统。

## 2. 主流程

```text
用户问题
  -> FastAPI 接口
  -> 问候语判断
  -> BM25 FAQ 检索
      -> 命中：MySQL 返回标准答案
      -> 未命中：进入 RAG
  -> 查询分类
  -> 检索策略选择
  -> Milvus 混合检索
  -> Reranker 重排
  -> Prompt 拼接
  -> DashScope 大模型流式生成
  -> MySQL 保存会话历史
  -> 返回给前端
```

## 3. 模块职责

| 模块 | 文件 | 职责 |
| --- | --- | --- |
| API 服务 | `app.py` | 提供 HTTP、WebSocket、静态页面 |
| 集成主流程 | `new_main.py` | 串联 FAQ、RAG、LLM、历史记录 |
| 配置 | `base/config.py` | 读取 MySQL、Redis、Milvus、LLM 配置 |
| FAQ 数据 | `mysql_qa/db/mysql_client.py` | 建表、导入 CSV、查询答案 |
| FAQ 检索 | `mysql_qa/retrieval/bm25_search.py` | BM25 + softmax 匹配 FAQ |
| 文档处理 | `rag_qa/core/document_processor.py` | 加载文档并做父子块切分 |
| 向量库 | `rag_qa/core/vector_store.py` | Milvus 建库、入库、混合检索、rerank |
| RAG 生成 | `rag_qa/core/new_rag_system.py` | 构造上下文和 Prompt，调用 LLM |

## 4. 今天要回答的问题

### 4.1 为什么先查 MySQL FAQ，再查 Milvus？

你的回答：

因为有的问题匹配阈值确实很高，直接返回结果就能解决问题；查 Milvus 是在没有匹配度特别高的时候再进行向量检索。

Mentor 批注：

这里说得对，但术语要更精确一点。当前项目里先判断的是 FAQ/BM25 的匹配阈值，不是 RAG 阈值。FAQ 命中时，答案来自人工整理过的 MySQL 标准问答，成本低、速度快、稳定性高；FAQ 没命中时，再进入 Milvus RAG，用向量检索处理更开放、更语义化的问题。

### 4.2 BM25 和向量检索各自适合什么问题？

你的回答：

BM25 更像关键词匹配，适合问题关键词和目标关键词比较多的情况。向量检索更像针对语义匹配的优化，主要针对语义相似。很多时候关键词做不到 100% 重合，所以需要向量检索。

Mentor 批注：

这个理解是对的。可以再补一句：BM25 对专有名词、明确术语、错误码、课程名、产品名很敏感；向量检索对同义表达、口语化提问、概念变体更友好。

### 4.3 Reranker 在项目里解决什么问题？

你的回答：

Reranker 是对匹配项的重新排序。主要是结合 BM25 和 RAG 的优势，关键词匹配语义不匹配、语义匹配关键词不太匹配，都可能得不到完全想要的结果。两者都匹配几乎一定是我们要的。Reranker 目的是结合两者优势找到真正需要的内容。

Mentor 批注：

方向非常好。再精确一点：当前项目里的第一阶段检索是召回，目标是“别漏掉可能相关的”；reranker 是精排，目标是“把最相关的排到前面”。它不是简单合并 BM25 和向量检索，而是用 cross-encoder 重新判断 query-document 的相关性，通常比单纯向量相似度更准，但更慢，所以只对候选集做。

### 4.4 为什么这个项目现在还不算完整 Agent？

你的回答：

因为这个项目还是针对问答功能，并没有调用后台完成任务的功能。

Mentor 批注：

这个判断很准。补充一下：它现在更像一条固定 RAG pipeline，流程由代码写死，系统没有自主决定“该调用哪个工具、是否继续追问、是否执行动作、是否校验和重试”的能力。Agent 的关键不是会聊天，而是能基于目标选择工具、执行动作、观察结果并继续决策。

### 4.5 Tool Calling 加进去后，系统会发生什么变化？

你的回答：

Tool Calling 加入后，项目就是一个真正的 Agent，能调用外部功能来完成项目。

Mentor 批注：

大方向对。更严谨地说，Tool Calling 是 Agent 化的关键一步，但还不等于完整 Agent。加入工具调用后，模型可以选择调用 FAQ、RAG、入库、评估、工单等工具；再配合状态管理、错误重试、答案校验、记忆和权限控制，才会更接近工程上的完整 Agent。

## 6. `IntegratedQASystem.query()` 阅读记录

我的理解：

1. 获取对话历史，记录对话日志。主要是看当前对话回答是否需要基于过往记忆进行综合性回答。
2. 执行 BM25 和 RAG 搜索。这一步进行真正的数据搜索。BM25 如果匹配度特别高，可以不进行 RAG。
3. 如果找到可靠答案，记录答案到日志中，并更新当前对话的历史。记录处理时间，返回答案。
4. else 线。如果 BM25 匹配度不足，需要进行 RAG 搜索，匹配到的内容除了要返回给用户，还需要留存一份作本地记忆。
5. 如果确实没有匹配的答案，那就记录这个问题确实没有合适答案，下次也没有。返回默认答案。

Mentor 批注：

整体控制流理解对了，尤其是“FAQ 命中就不走 RAG，未命中再回退 RAG”这一点抓得很好。下面是需要修正的细节：

- 第 2 点：代码不是“执行 BM25 和 RAG 搜索”，而是先执行 BM25。只有 `need_rag == True` 时，才调用 `self.rag_system.generate_answer(...)`。
- 第 4 点：RAG 匹配到的内容不会写入知识库，也不是“本地记忆”。代码里保存的是最终生成的完整回答，用 `update_session_history()` 写入 MySQL 的 `conversations` 表，作为后续多轮对话历史。
- 第 5 点：没有匹配答案时只是记录日志并返回默认答案，并不会把“这个问题没答案”写成长期记忆。下次问同样问题，系统仍会重新走一遍检索流程。

更准确的流程：

```text
query()
  -> 记录开始时间和日志
  -> 如果有 session_id，读取最近 5 轮历史
  -> BM25 FAQ 检索
      -> 有 answer：保存历史，yield answer, True
      -> need_rag：调用 RAG 生成流式答案，收集完整答案，保存历史，yield "", True
      -> 否则：返回默认未找到答案
```

## 7. `BM25Search.search()` 阅读记录

我的理解：

1. `cached_answer = self.redis_client.get_answer(query)` 如果命中，会返回缓存答案和 `False`。这似乎是命中了 Redis 中存储过的过去问过的问题，会直接返回缓存。
2. 如果数据库中没有可靠答案，就返回 `(None, True)`。出现错误被捕捉也是返回 `(None, True)`。目前还不太理解两个字段的含义。

Mentor 批注：

你对 Redis 缓存的判断是对的。这里的缓存作用是：如果同一个 query 之前已经匹配到过答案，就不用重新分词、算 BM25、查 MySQL，直接返回缓存答案。

两个返回字段可以这样理解：

```python
answer, need_rag = bm25_search.search(query)
```

- `answer`：FAQ/BM25 阶段找到的答案。如果是字符串，说明 FAQ 可以回答；如果是 `None`，说明 FAQ 阶段没有答案。
- `need_rag`：是否需要回退到 RAG。`False` 表示不用 RAG，`True` 表示需要 RAG。

因此返回值语义是：

| 返回值 | 含义 | 后续动作 |
| --- | --- | --- |
| `(cached_answer, False)` | Redis 已缓存答案 | 直接返回 |
| `(answer, False)` | BM25 命中高相似 FAQ，并从 MySQL 查到答案 | 直接返回 |
| `(None, True)` | FAQ 没有可靠答案 | 进入 RAG |
| `(None, True)` | FAQ 检索出错 | 为了不中断服务，回退到 RAG |

关键点：

- `False` 不是“失败”，而是“不需要 RAG”。
- `True` 不是“成功”，而是“需要 RAG 接手”。
- 这个函数的职责不是最终回答用户，而是判断 FAQ 这一层能不能解决问题。
